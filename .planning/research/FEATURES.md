# Feature Research

**Domain:** Unraid Community Applications Docker Containers
**Researched:** 2026-02-01
**Confidence:** MEDIUM-HIGH

## Feature Landscape

### Table Stakes (Users Expect These)

Features users assume exist. Missing these = product feels incomplete or won't be approved by Community Applications.

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Persistent appdata volume | All Unraid containers store config in `/mnt/user/appdata/<app>` | LOW | Map container `/config` or app-specific path to `/mnt/user/appdata/openclaw/` |
| PUID/PGID environment variables | Standard for file ownership (99:100 = nobody:users) | LOW | Prevents root-owned files, allows host access. LinuxServer.io standard. |
| WebUI access configuration | Users expect click-to-access from Unraid Docker tab | LOW | Template `WebUI` field with pattern `http://[IP]:[PORT:8080]/` |
| XML template for Community Apps | Only supported distribution method for Unraid | MEDIUM | Must follow schema, auto-generated by Unraid preferred |
| Support thread on Unraid forums | Community Applications submission requirement | LOW | Dedicated forum thread for troubleshooting and support |
| Icon and banner URLs | Visual identification in Docker tab and CA store | LOW | HTTPS PNG URLs for professional appearance |
| Auto-start capability | Containers should start when array starts | LOW | Built into Unraid, just needs proper template config |
| Volume path mappings | Data/config separation from container image | LOW | Standard Docker practice, critical for updates |
| Environment variable configuration | Runtime customization without rebuilding | LOW | Timezone (TZ), paths, app-specific settings |
| Bridge networking by default | Safest, most compatible network mode | LOW | Isolated network with explicit port mappings |

### Differentiators (Competitive Advantage)

Features that set the product apart. Not required, but valuable.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Branch/tag selection in template | Users can choose stable vs beta versions | MEDIUM | Allows `latest` and `beta` branches without manual editing |
| Pre-configured sensible defaults | Works out-of-box, minimal user configuration | LOW | Default paths, ports, settings aligned with OpenClaw expectations |
| Clear installation documentation | Reduces support burden, improves adoption | LOW | README with setup steps, common issues, configuration guide |
| Automatic permission fixing | Container handles PUID/PGID application internally | MEDIUM | Entrypoint script sets ownership on mapped volumes |
| Health check implementation | Unraid shows container health status | MEDIUM | Docker HEALTHCHECK directive, reports if service is actually running |
| Update notifications | Users see when new versions available | LOW | Proper image tagging on DockerHub enables CA update detection |
| Minimal image size | Faster pulls, less storage, better perception | MEDIUM | Alpine-based images, multi-stage builds, only essential dependencies |
| Example configuration files | Speeds up first-time setup | LOW | Provide sample configs in `/config` on first run |
| Detailed changelog in template | Users know what changed between versions | LOW | Template `Changes` field for template updates |
| Extra search terms in template | More discoverable in CA store | LOW | `ExtraSearchTerms` field with related keywords |

### Anti-Features (Commonly Requested, Often Problematic)

Features that seem good but create problems.

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Docker Compose support | Familiarity from other platforms | Unraid doesn't natively support compose, requires plugins | Use standard XML template, it's the Unraid way |
| Privileged mode by default | "Makes things work" with less config | Major security risk, gives container full host access | Use only when absolutely necessary (hardware access), document why |
| Root user execution | Simpler permission model | Files become inaccessible to host, security risk | Always implement PUID/PGID, run as non-root inside container |
| Hardcoded paths in container | Simplifies Dockerfile | Breaks Unraid conventions, confuses users | Follow `/config` for appdata, configurable volume mounts |
| Auto-update within container | Users want "set and forget" | Can break container, Unraid handles updates via CA | Let Unraid/CA handle updates, don't update binary inside container |
| Bundling multiple services | "All-in-one" convenience | Violates Docker best practices, harder to debug/update | One service per container, use Docker networking to connect |
| Custom entrypoint override | Advanced user control | Breaks in Unraid environment, limited support | Build flexibility into default entrypoint with env vars |
| In-place binary upgrades | Seems efficient | Unraid doesn't support, could break container | Always update via image replacement, not internal upgrades |

## Feature Dependencies

```
[XML Template]
    ├──requires──> [DockerHub Published Image]
    ├──requires──> [Icon/Banner URLs]
    └──requires──> [Support Thread]

[Persistent Storage]
    └──requires──> [PUID/PGID Configuration]
                       └──enables──> [Host File Access]

[WebUI Access]
    └──requires──> [Bridge Network + Port Mapping]

[Community Applications Approval]
    ├──requires──> [XML Template]
    ├──requires──> [Support Thread]
    ├──requires──> [Open Source License]
    └──requires──> [No Conflicts with Core Unraid]

[Health Checks] ──enhances──> [Auto-restart Capability]

[Branch Selection] ──requires──> [Multiple Tags on DockerHub]
```

### Dependency Notes

- **XML Template requires DockerHub Published Image:** Can't distribute template without published container
- **Persistent Storage requires PUID/PGID:** Without proper UID mapping, files become root-owned and inaccessible
- **WebUI Access requires Bridge Network + Port Mapping:** Bridge mode requires explicit port exposure for accessibility
- **CA Approval requires all submission elements:** Missing any requirement delays or blocks approval
- **Health Checks enhance Auto-restart:** With healthcheck, can configure auto-restart on failure
- **Branch Selection requires Multiple Tags:** Need both `latest` and `beta` (or similar) tags published to DockerHub

## MVP Definition

### Launch With (v1)

Minimum viable product — what's needed to get into Community Applications and provide core value.

- [x] **DockerHub published image** — Can't distribute without it
- [x] **Persistent ~/.openclaw/ volume mapping** — Core value prop: config survives restarts
- [x] **PUID/PGID environment variables** — Table stakes for Unraid, prevents permission issues
- [x] **Basic XML template** — Name, Repository, Network, Support, Icon, WebUI, basic Config entries
- [x] **WebUI access configuration** — Users need to access OpenClaw interface from Unraid
- [x] **Support thread on Unraid forums** — Required for CA submission
- [x] **Icon URL (HTTPS PNG)** — Visual identification in Docker tab
- [x] **Bridge networking with port mapping** — Standard, safe default
- [x] **Appdata volume mapping** — `/mnt/user/appdata/openclaw/` to container config path

### Add After Validation (v1.x)

Features to add once core is working and getting user feedback.

- [ ] **Health check implementation** — Shows container status, enables auto-restart on failure (when users report stability issues)
- [ ] **Branch/tag selection** — Allow choosing between stable/beta (when beta testing begins)
- [ ] **Banner URL** — Enhanced visual appeal in CA store (when driving adoption)
- [ ] **Enhanced documentation** — Detailed README, troubleshooting guide (based on support thread questions)
- [ ] **Example configuration files** — Pre-populated sample configs (when common config patterns emerge)
- [ ] **Changelog in template** — Track template evolution (after several template updates)
- [ ] **Extra search terms** — Improve discoverability (after analyzing how users search)
- [ ] **Automatic permission fixing** — Entrypoint script to handle ownership (if PUID/PGID causing issues)

### Future Consideration (v2+)

Features to defer until product-market fit is established.

- [ ] **Multiple architecture support** — ARM/ARM64 builds (when demand from Pi/ARM users exists)
- [ ] **Advanced environment variables** — Fine-tuned control options (when power users request it)
- [ ] **Optimization for minimal image size** — Alpine base, multi-stage builds (when storage/bandwidth becomes concern)
- [ ] **Integration with CA Auto-Update plugin** — Automated update support (post-launch stability)
- [ ] **Custom startup scripts** — PostArgs for initialization (when advanced use cases emerge)
